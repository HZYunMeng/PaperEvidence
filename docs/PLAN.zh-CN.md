# 科研论文助手实施与开源计划

项目目标是做一个有人愿意使用和贡献的学术论文助手，并争取进入 GitHub Trending。上榜取决于外部关注和平台排序，不能承诺。第一阶段先证明：用户能轻松找到答案对应的论文证据，并能发现系统回答错误的位置。

本计划按 C++ 与 Python 基础、每周 10–20 小时、可投入预算设计。建议先用 Python 完成一个可复现流程，真实使用后再决定是否需要 C++ 优化。以下 6–8 周是工作量估计，不是完成承诺；解析器、模型与预算确定后再细化。

## 定位与差异化

原始 README 的方向是多模态学术 RAG，适合 AI 工程学习，但章节切片、向量检索、重排和 PDF 聊天已有大量实现。建议把第一版对外表述收窄为：**论文问答的每条结论，都能回到可检查的原文、页码和图表位置。**

可演示场景是用户提问“论文中方法 A 在数据集 B 上的准确率是多少”，界面展示对应表格、明确行列、原文页码，并在缺失证据时拒答。接下来增加证据删除或错误表格注入，展示系统是否会继续编造数值。图像描述仅是辅助检索信号；不应把视觉模型生成的描述当作论文原始事实。

| 对照项目 | 已有能力 | 我们需要验证的切入点 |
| --- | --- | --- |
| [PaperQA](https://github.com/Future-House/paper-qa) | 科学文档问答、引用、检索与重排 | 面向学生的证据检查操作是否更容易；不能声称它不支持多模态 |
| [RAG-Anything](https://github.com/HKUDS/RAG-Anything) | 文本、图像、表格、公式的多模态 RAG | 更小的安装与演示范围；论文具体失败案例是否更清楚 |
| [Docling](https://github.com/docling-project/docling) | 文档结构、阅读顺序、表格、公式与 OCR | 优先接入解析器，把工作放在来源映射与评测 |
| [pdfplumber](https://github.com/jsvine/pdfplumber) | 文本与表格解析、位置坐标 | 当前轻量基线，不能代表完整多模态理解 |

以上比较依据 2026 年 10 月 8 日查阅的项目说明；能力可能变化。这些是产品假设，需要访谈和实验，而非已经证明的独有优势。

## 第一阶段现状

已有可运行的 Streamlit 页面、PDF 文本与有边框表格解析、章节和页码分块、BM25 检索、原文区域高亮、JSON 导出、可选 Ollama 生成接口、引用与数值校验、检索对照脚本和自动化测试。

第二轮已增加本地多语言 E5 语义检索、排名融合、token 窗口、向量缓存、云端兼容生成接口与预算限制。实际运行了 E5 的中英配对虚构示例评测；生成接口仅完成离线测试，真实生成仍待模型配置。详见 [验证记录](VERIFICATION.zh-CN.md)。

当前引用校验仅证明引文存在，以及答案中的数值是否出现在引文里，不能证明结论被引文蕴含。相同数值可能来自错误表格行；单元格绑定提供来源定位，但不证明模型选择了正确实验设置。

第三轮建立了单元格引用与三篇真实论文开发集。第四轮补上常见双栏阅读顺序、横线表格行列恢复和长表格按行分块；六个目标表格事实现在均可绑定来源坐标，BM25 在开发题上召回 18/24，表格题单元格召回 10/12。语义与融合仍未优于 BM25。下一步复核标注，选择独立论文，再补生成与证据扰动评测，详见 [真实评测报告](REAL-EVAL.zh-CN.md)。

## 开发顺序

| 阶段 | 估计投入 | 交付与验收 |
| --- | --- | --- |
| 第 1–2 周 | 20–35 小时 | 使用 3–5 篇真实论文跑通上传、检索、引用和回答；标注双栏与表格解析失败；确定模型和运行方式 |
| 第 3–4 周 | 20–40 小时 | 接入一个布局解析器；表格保留单元格、表头与页码；接入一个多语言 embedding 和一个 reranker；跑真实基线 |
| 第 5–6 周 | 20–40 小时 | 图片区域与图注绑定；可选视觉模型处理检索到的图像；完成真实 QA、无答案问题和证据扰动评测 |
| 第 7–8 周 | 15–30 小时 | 修复首次体验；英文文档与中文教程；短演示与实验报告；邀请测试后发布 v0.1 |

首先支持文本型论文和表格。扫描件、公式转 LaTeX、跨页表格、多人知识库、综述 Agent、错题生成可以按真实需求分批增加。原始 README 同时列出的所有能力不应作为第一版发布条件。

后端先保留清晰的解析、分块、检索、生成、校验接口。当前使用 JSON 保存来源索引、NumPy 保存本地向量缓存；小规模先直接计算相似度，数据扩大后再按实测需求接向量数据库。若使用 FastAPI，应在需要复用 API 或更换前端时添加，避免维护两套重复业务逻辑。LangChain 与 LlamaIndex 二选一也不是当前必需条件。

## 真实评测设计

初始目标是 8–12 篇允许使用的论文、100–150 个问题；规模需随标注质量调整。按论文划分开发集与保留测试集，减少同论文结构和问答泄漏。记录来源许可与下载方式，不默认把所有论文 PDF 放进公开仓库。

问题应包含正文事实、表格数值、图表趋势、跨段综合和无法从论文回答的问题。每题记录论文 ID、问题语言、参考答案、证据页码、原文或表格单元格、模态、是否可回答、标注人和复核意见。先用人工一致性检查纠正含糊问题。

| 指标 | 定义和用途 |
| --- | --- |
| Evidence Recall@k | 正确证据是否进入 top-k；表格需定义正确行列，不只找到表格 |
| 数值准确率 | 数值、单位、实验设置和对应方法是否同时正确 |
| 引用支持率 | 人工检查引用是否支持该条结论；原文引文存在率单独报告 |
| 不支持结论比例 | 回答中的事实性结论有多少没有证据；注明人工或模型裁判方法 |
| 无答案拒答率 | 无答案问题有多少被拒答，同时报告有答案问题的错误拒答率 |
| 覆盖率与选择性错误率 | 已回答问题占比，以及这些回答中的错误率，避免通过全部拒答得到好指标 |
| 成本与延迟 | 解析耗时、每题调用与 token、运行硬件、模型版本和 API 实际费用 |

基线与优化方案使用同一批论文、生成模型、提示词、候选数量及上下文预算。分别消融章节分块、结构化表格、重排、拒答与视觉证据，区分是哪一步产生变化。OCR 或解析器对照要独立实验，不同时更换所有模块。检索分数阈值只能在开发集上调整，不能称为天然置信度。

报告失败案例与重复运行波动。质量结论来自保留测试集；在实验前不写“显著提升”“大幅降低”。若要声称统计显著，应明确检验、置信区间及样本单位。当前 `eval/smoke-results.json` 是 7 个虚构示例问题的流程测试，两种方案在此数据上持平，不证明真实场景性能。

## 如何投入预算

先把预算用在小规模真实评测、难例视觉解析和测试者反馈。云模型适合快速开始，本地模型适合有合适硬件且愿意维护环境的情况；价格和性能在选定供应商后核查。不要先买 GPU 或训练大模型。每轮实验先限制文档数、页数、问题数和调用数，确认实际账单后扩量。

API Key 放在环境变量或本地 secrets 文件，不写到 README 或仓库。接入云服务时，在界面明确显示会发送哪些论文内容，用户自行选择模式。

## 发布准备与传播

首发验收建议：新用户在干净环境中按 README 启动成功；至少 5 位目标用户实际测试；核心流程无阻断错误；完成有失败案例的真实评测；提供可合法分发的示例；明确哪些功能已实现；英文 README 首屏能解释使用价值。

30 秒演示展示一个问题、答案、表格行列和 PDF 来源位置，再展示一个无法回答的问题。配一篇技术文章，解释章节与表格来源如何保留，以及哪些幻觉仍然挡不住。所有对比数字来自公开可复现实验。

发布时准备 GitHub 描述、截图、安装命令、版本说明、贡献指南、许可证、5 个适合新贡献者的问题。向论文阅读者、同学、导师和 RAG 开发者收集反馈；在符合规则的社区分享具体失败案例和可运行演示，社区发帖需要用户亲自发布或明确授权。

发布后一周优先修复安装失败和证据错误，记录独立用户成功使用、复用和贡献的情况。Star、fork、issue 和是否进入 Python 或全语言 Trending 可作为传播结果，但不设“达到某个 Star 数必然上榜”的阈值。

GitHub 在[早期官方说明](https://github.blog/news-insights/company-news/explore-what-is-trending-on-github/)中提过多种互动信号与时间因素，这不能当作当前排序公式。此次取得的 Trending 页面有缓存延迟，不能作为 2026 年 10 月 8 日的实时排名。

## 下一步最有价值的工作

复核当前 12 个事实，选择未参与开发的新论文，并接入用户选定的生成模型验证回答。优先加入错误行、缺失证据和单位错误扰动，记录正确回答、错误回答和错误拒答。发布前仍需在干净环境安装并邀请真实用户试用。
